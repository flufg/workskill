# 客户侧 Bug 信息采集脚本规范

仅在现有证据无法区分关键假设或需要捕获再次复现时使用。脚本的目标是回答具体诊断问题，不是复制整机数据。

生成脚本前，主机角色、路径、unit、设备、接口和输出策略必须由工程师在本次 Bug 上下文中确认，不从历史命令、其他客户脚本或持久化环境配置中猜测。脚本、manifest 和交付说明不嵌入 SSH/向日葵/ToDesk 凭据、客户访问信息或与采集无关的环境细节。

## 1. 先写采集设计

生成脚本前列出：

| 项目 | 内容 |
|---|---|
| 待验证假设 | 脚本要区分哪些可能原因 |
| 故障对象 | 应用、unit、PID、设备、接口、挂载点、session 或容器 |
| 时间窗口 | 明确起止时间、时区、当前或上次 boot |
| 数据来源 | 每项命令回答什么问题 |
| 权限 | 普通用户数据与可选 root 数据分开 |
| 资源上限 | 最大运行时间、单文件大小和总包大小 |
| 敏感内容 | 可能出现的账号、Token、路径、IP 或业务数据 |

若无法填出“待验证假设”和“每项命令回答什么问题”，不要生成脚本，先补充故障上下文。

## 2. 脚本硬性要求

生成 Bash 脚本，并满足以下约束：

- 以只读采集为默认行为，不修改配置、不重启服务、不安装软件、不复现高风险动作。
- 采集脚本是诊断产物，不得编辑、替换、编译、安装或删除客户产品源码、二进制、构建文件、依赖和测试。
- 不访问网络、不自动上传、不调用远程 URL；产物只保存在客户本机。
- 使用 `umask 077`，创建唯一输出目录，禁止跟随不受控路径或覆盖已有文件。
- 所有变量加引号；校验 case ID、unit、PID、接口等输入；禁止 `eval` 和字符串拼接执行命令。
- 命令缺失、权限不足或某一项失败时继续采集，在 manifest 中记录退出码和错误，不能静默跳过。
- 对每条可能卡住的命令设置合理 timeout；限定 journal 时间窗、grep 上下文、进程/设备对象和输出行数。
- 默认不收集 `/proc/*/environ`、完整命令行、core、pcap、浏览器数据、用户文档、SSH 密钥或整个 home。
- root 采集必须是独立、可选的 `--allow-sudo` 模式；默认不主动调用 `sudo`，也不假定客户具有免密 sudo。
- 不使用宽泛递归 `find /`、全量 `journalctl`、全系统 `lsof`、无限 `dmesg -w` 或无边界抓包。
- 保留原始命令输出，同时生成 manifest：采集时间、时区、主机、脚本版本、参数、命令、退出码、文件大小和缺失项。
- 压缩前给客户列出文件清单和敏感性提示；生成 `.tar.gz` 和 SHA-256。不得加密后隐藏内容供客户无法检查。
- 脚本结束时打印产物路径、大小、校验值、未成功项目、预览方法和清理命令；不自动删除原始目录。

## 3. 建议结构

脚本应清晰包含：

1. 只读说明、兼容范围、预计时长/空间和用法。
2. 参数解析与严格校验。
3. 安全输出目录和 manifest 初始化。
4. `run_collect` 函数：记录命令标签、开始/结束时间、退出码和 stderr。
5. 通用最小基线：时间、发行版、内核、boot/session 边界。
6. 与当前假设对应的定向模块。
7. 可选、显式授权的 sudo 模块。
8. 文件清单、人工脱敏提示、归档和校验值。

不要为了“通用”把所有模块同时放入脚本。仅保留当前事件需要的模块，例如：

- 登录黑屏：session、display manager、用户 journal、DRM/GPU、home 空间和关键权限。
- 服务被杀：目标 unit/PID、内核 OOM、cgroup memory.events/limits 和资源趋势。
- 只读挂载：目标 mount、块设备、故障窗口内核 I/O/文件系统错误；不做写入测试。
- 应用权限错误：执行身份、逐级路径权限、ACL、LSM denial、沙盒声明权限。
- 网络超时：目标 DNS、route、socket/TCP/TLS 分层；抓包必须作为另行授权的 L1 方案。

## 4. 脱敏策略

自动替换适合结构明确的秘密，例如常见 Authorization、Bearer、password、secret、token 字段；保留原始文件只能放在权限为 0700 的本地目录中。

不要承诺自动脱敏能覆盖所有客户数据。归档前必须：

- 打印待打包文件列表。
- 提供 `less`/编辑器预览方法和敏感关键词搜索建议。
- 提醒客户检查用户名、主机名、IP、路径、业务载荷和截图。
- 说明删除某项证据可能降低哪条假设的判断能力。

## 5. 交付前验证

- 必须运行 `bash -n <script>`。
- 有 `shellcheck` 时运行 `shellcheck <script>` 并处理适用告警。
- 在隔离的临时目录执行一次普通用户路径，确认不会修改系统状态或访问网络。
- 检查缺少可选命令时仍能结束并生成 manifest。
- 检查输出目录已存在时不会覆盖，参数含空格或特殊字符时不会命令注入。
- 检查归档内容、权限、大小、SHA-256 和清理提示。

无法执行某项验证时，在交付说明中列为“未验证”，不能隐藏。

## 6. 停止条件

第一轮脚本仅收集区分当前 1–3 个假设所需的数据。分析第一轮产物后：

- 足以定责：停止采集并形成结论。
- 暴露一个明确缺口：生成范围更窄的第二轮脚本。
- 仍无方向：重新审视症状、时间线和复现条件，不通过扩大采集范围碰运气。

涉及 core、pcap、性能追踪、复现 suspend、重启或其他 L1–L3 操作时，不放入默认采集脚本；作为单独方案说明风险并等待授权。
