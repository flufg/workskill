# 解决方案与 Bug 分析报告规则

根因达到“已证实”或“高”置信度时使用。中/低置信度只能输出条件性方案，并将报告标记为草稿。输出方案的默认终点是“等待决策”，不是实施。本 Skill 不修改产品代码。

## 产品代码边界

- 可以只读检查源码、符号、调用链、配置和构建信息，以定位根因及影响范围。
- 不编辑产品源码、头文件、构建脚本、依赖锁文件、测试、安装包或发布配置。
- 不生成可直接应用的产品补丁，不创建 commit、分支或 PR，不代替开发团队实现或重构。
- 需要代码改动时输出“开发实施说明”：根因机制、受影响模块/接口、建议修改方向、兼容与迁移风险、测试矩阵、发布约束和回滚要求。
- 不虚构具体文件、函数、行号或 diff。只有证据明确时才记录代码定位结果。
- 客户信息采集 Bash 脚本和 Markdown 分析报告属于诊断产物，不属于产品代码修改，但仍需遵守安全、脱敏和验证规则。

## 1. 判断 Bug 性质

根因和 Bug 性质是两件事：根因说明“为什么发生”，性质判断决定“由谁、以什么级别处理”。选择一个主类型，必要时标注交叉类型：

| 类型 | 判断信号 | 常见处理路径 |
|---|---|---|
| 应急事件 | 影响正在扩大、核心能力不可用、需要先恢复服务 | 可逆止损后继续评估，不把止损当永久修复 |
| 局部实现缺陷 | 原因集中在单个模块、配置或边界条件，接口和架构仍成立 | 小范围修复或优化，并做针对性回归 |
| 系统性设计问题 | 多模块重复出现、状态模型或接口假设失效、局部补丁会继续积累 | 部门评估重构、重做或架构演进 |
| 产品/需求问题 | 当前行为符合实现但不符合用户目标，或需求边界冲突 | 产品、研发、测试共同确认预期和验收标准 |
| 第三方/环境问题 | 外部依赖、驱动、内核、硬件或客户环境是主要条件 | 兼容策略、供应商协同、环境约束或客户端缓解 |
| 安全/数据风险 | 涉及越权、泄露、完整性、不可逆数据损坏或合规 | 优先隔离和升级响应，限制证据与方案传播范围 |

性质判断至少考虑：影响严重度和范围、是否仍在扩大、复现频率、数据/安全风险、根因是否局部、跨模块耦合、历史复发、兼容和迁移成本、测试覆盖、修复时效与工程投入。

证据不足以判断性质时写“待部门评估”，列出需要产品、研发、测试、运维、安全或其他责任方确认的问题，不替他们做组织决策。

## 2. 选择处理路径

处理路径使用以下之一或组合：

- **仅应急处理**：先控制客户影响，设置有效期和退出条件，后续仍要决定是否永久修复。
- **局部修复/优化**：范围明确、架构前提仍成立，能够用目标化修改和回归测试闭环。
- **重构/重做评估**：局部修补不能消除系统性风险，或涉及接口、协议、数据模型、公共组件和多团队协作。
- **第三方/环境协同**：明确客户端可控缓解、外部责任边界、版本约束和证据交付。
- **接受风险/延期**：记录影响、理由、风险所有者、监控阈值、重新评估条件和截止时间。

需要部门评估时，至少给出“局部优化”和“重构/重做”两类可比方案，比较：根因覆盖度、改动范围、兼容/迁移、研发测试成本、上线风险、回滚难度、预期收益、遗留风险和后续维护成本。可以提出倾向性建议，但必须明确最终决定人和仍待确认项。

## 3. 从根因推导候选方案

解决方案必须直接对应已经建立的故障机制，不能用重启、重装、扩大权限、关闭安全策略或清空数据替代因果修复。

按需给出三个层次：

| 层次 | 目的 | 要求 |
|---|---|---|
| 临时止损 | 控制影响或恢复最低可用能力 | 改动最小、持续时间明确、可撤销，不掩盖后续证据 |
| 根因修复 | 消除已确认的故障机制 | 精确到目标配置、版本、代码、设备或策略，避免扩大修改范围 |
| 永久治理 | 防止再次发生或缩短发现时间 | 回归测试、兼容矩阵、容量阈值、监控、告警、发布或回滚机制 |

每个候选方案记录：

- 解决的根因和适用前提
- 具体修改内容、目标对象和版本范围
- 用户数据、业务、会话、性能和兼容性影响
- 所需权限、维护窗口和恢复通道
- 风险等级与失败模式
- 回滚触发条件、回滚步骤和回滚后的验证
- 修复验证步骤和合理观察窗口

存在多个方案时给出简短比较并推荐一个。推荐理由应基于风险、可逆性、根因覆盖度和长期维护成本，而不是只选择最快的方案。

## 4. 不同根因类型的方案要求

- **代码缺陷**：只读定位组件、函数或调用路径，说明触发输入和错误机制；输出开发实施说明、受影响版本、单元/集成/回归测试及发布回滚要求。不得编辑代码或生成产品补丁；没有源码或符号证据时不要虚构文件、行号或修改内容。
- **配置或权限**：指出实际生效配置、运行身份和冲突来源；使用最小权限或最小配置差异，保留原值和配置验证命令。
- **资源或容量**：区分泄漏、峰值、限额和外部压力；调整阈值只能作为有容量依据的方案，不能代替修复泄漏或无界队列。
- **依赖、驱动或内核**：说明兼容组合和受影响范围；升级、降级或回滚必须保留可启动版本、控制台和包恢复路径。
- **存储或硬件**：优先保护数据和冗余；修复、替换或文件系统操作必须满足备份、卸载/停机和恢复条件。
- **第三方或环境问题**：记录责任边界和客户端可控缓解，同时给出供应商证据、版本约束和退出缓解的条件。

## 5. 决策与外部实施记录

给出方案不等于获得执行权限，根因确认也不等于方案已批准。状态必须使用以下之一：

- 建议：分析方给出的候选方案
- 待部门评估：需要责任部门选择优化、重做、延期或其他路径
- 已批准应急处理：仅批准明确的临时止损范围
- 已批准优化：已确认局部修复范围、版本和验收标准
- 已批准重做：已确认重构/重做目标、迁移策略和负责人
- 外部已执行：根据用户或实施团队提供的命令、配置/代码 diff、版本、时间和执行结果记录
- 已验证：原始症状和回归验证均符合预期
- 已回滚：记录触发原因、回滚内容和回滚后状态

默认在提交建议和分析报告后停止。代码实现始终交给后续开发流程；即使方案已经批准，本 Skill 也只更新决策状态和开发实施说明，不修改产品代码。

外部实际执行偏离已批准方案时，在报告中同时保留批准内容和实际操作，标记偏差并建议重新评估风险，不覆盖历史。

## 6. 验证与停止条件

修复验证至少包括：

- 原始故障条件下症状消失
- 直接根因信号消失或回到正常范围
- 服务、日志、资源和关键业务路径正常
- 相邻版本、节点、用户、协议或设备路径没有明显回归
- 经过与故障频率匹配的观察窗口未复发
- 回滚仍然可用，临时缓解和诊断设置已经清理

出现以下情况时停止扩大修改并回滚或重新诊断：

- 原始症状仍存在
- 出现新的高严重度错误或数据风险
- 关键指标明显恶化
- 实际环境与方案前提不符
- 无法确认修改对象、备份或恢复路径

## 7. 报告落盘规则

默认生成 Markdown 报告：

```text
bug-reports/<case-id>-<YYYYMMDD-HHMMSS>.md
```

- 优先使用用户指定的报告路径和命名规则。
- case ID 仅保留字母、数字、点、下划线和连字符；无法获得 case ID 时使用简短症状标识。
- 报告头部记录状态：草稿 / 根因已确认 / 待部门评估 / 应急处理待批准 / 优化已批准 / 重做已批准 / 修复已验证 / 已回滚。
- 同一事件更新已有文件，并在修订记录中追加时间、作者/执行主体和变更摘要。
- 大段日志、图片、core、pcap 和采集包作为受控附件引用，不嵌入报告；记录路径、权限和 SHA-256。
- 报告不得包含密码、Token、Cookie、私钥或未经脱敏的客户业务数据。
- 无法写文件时输出完整 Markdown，并明确报告未落盘及原因。

报告必须可区分已观察事实、分析推断、建议方案和实际执行结果。未知项写“未知/未验证”，不能用空白掩盖。
