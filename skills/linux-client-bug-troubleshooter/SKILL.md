# Linux 客户端 Bug 排查

从用户可见症状向下追踪到应用、桌面会话、系统服务、权限、存储、网络、内核驱动和硬件，形成可复核的根因证据链。诊断请求默认只调查和报告；只有用户明确要求修复时才改变目标系统状态。

## 0. 确定当次排查方式

客户环境只用于当次 Bug 排查，不建立、更新或复用客户环境 Profile，不把客户主机、拓扑、路径、设备号或访问方式当作 Skill 配置保存。根据当前可用条件选择一种工作方式：

- **离线材料分析**：分析工程师已提供的描述、图片、错误码、日志和采集包。
- **SSH 排查**：只使用工程师本轮明确授权且已建立的 SSH 会话或当次连接信息，优先执行限定范围的只读命令。
- **向日葵/ToDesk 远程桌面排查**：在工程师或客户已建立当次授权会话后，使用可用的计算机操作能力查看界面、日志和系统状态。
- **工程师转交**：无法直接访问客户环境或证据不足时，向工程师输出可直接转发给客户的材料收集清单或采集脚本，由工程师与客户协调。

SSH 密码、私钥、跳板机凭据、向日葵/ToDesk 设备号、验证码和临时密码只能用于当次授权会话；不写入 Skill、报告、脚本、终端命令历史或仓库。无明确授权、会话不可用或操作范围不清晰时，退回离线分析和工程师转交方式。

## 核心原则

- 先保护现场，再缩小范围；先只读、低影响和可逆操作。
- 不按关键词、单张截图或最后一行日志直接定责。区分事实、推断和待验证项。
- 把 GUI 症状视为跨层故障入口，不因“客户端问题”跳过内核、存储、权限、cgroup 或系统服务。
- 维护 1–3 个可证伪假设；每次只收集能区分这些假设的证据。
- 缺少日志、权限、工具或时间上下文是证据限制，不等于没有异常。
- 重启、重装、切换显示协议或关闭安全策略只能作为经授权的对照或缓解，不能替代根因。
- 产品代码只读：可以阅读源码、配置和构建信息来定位机制，但不得编辑源码、构建脚本、依赖或测试，不生成或提交产品补丁、commit、分支或 PR。
- 允许创建的产物仅限客户信息采集脚本和 Bug 分析报告；采集脚本不得修改、替换或构建客户产品代码。

## 1. 解析输入证据

用户可能提供文字描述、照片/截图、错误码、日志文件或它们的组合。先建立统一的事件记录：

- 实际现象、期望行为、影响范围和复现步骤
- 首次/最近发生时间、时区、频率和当前状态
- 故障前相关变更及已经尝试的操作
- 发行版、内核、客户端/服务版本、桌面环境、包类型和硬件环境

按输入类型处理：

- **文字描述**：提取可观察事实，不把用户的原因判断直接当作事实；标出含糊的时间、对象和动作。
- **现场照片或错误截图**：使用可用的图像查看能力完整检查原图，逐字转录关键错误、错误码、窗口标题、时间和状态标识。区分“图中可见”与“根据画面推测”；不要臆测裁剪区域。关注拍摄反光、模糊、截断、屏幕外信息和隐私数据，必要时请求原始日志或更清晰原图。
- **错误码/报错文本**：保留精确大小写、数值、模块和调用上下文；结合版本和执行阶段解释，不能只按错误字符串检索结论。
- **日志**：保留时间戳、时区、boot/session、主机/容器、PID/TID 和前后文；按时间关联客户端、system/user service、内核和设备日志。识别首次异常、连锁错误和恢复动作，不把最后一条错误默认当根因。

不同证据冲突时，明确记录冲突并设计对照，不静默选择其中一个。

输入材料不足以建立有效假设或缺少关键时间线时，完整读取 [排查材料清单规则](references/material-request-checklist.md)，向工程师输出本次需要的最小材料清单。不直接假定客户能执行命令，不把所有可能材料做成无差别长清单。

## 2. 建立假设与排查路径

给出或执行命令前完整读取 [证据与命令安全](references/evidence-safety.md)。根据故障选择一个主路径和必要的交叉路径：

| 路径 | 典型范围 | 读取参考 |
|---|---|---|
| 客户端/桌面 | GUI 应用、X11/Wayland、显示/GPU、登录、输入、音视频、无线、休眠、Flatpak/Snap/Portal | [桌面与客户端排查手册](references/desktop-triage-playbook.md) |
| 系统/运行环境 | 进程、systemd、资源、网络、存储、内核、权限、依赖、启动、容器/cgroup | [系统排查手册](references/system-triage-playbook.md) |

只读取当前相关的章节；跨层症状可以同时读取两个手册。对每个活跃假设记录：

- 支持证据
- 反对证据
- 缺失证据
- 下一项最低风险、最高区分度的验证

远程协作时每轮优先给出 1–3 项检查，说明目的、执行位置、权限、风险、范围和预期信号。能直接访问受控环境时，可以自行执行安全、只读且范围明确的检查。

## 3. 判断证据是否足够

只有满足以下条件，才输出确定性根因：

- 关键时间线能够闭合
- 直接触发因素有原始证据支持
- 候选原因之间已有区分性证据
- 反事实与实际现象吻合
- 证据能解释影响范围和复现条件

否则输出“最可能假设”和当前置信度，并进入定向采集，不要为了给出答案而过度推断。

## 4. 证据不足时生成客户采集脚本

当已有描述、图片和日志不能区分关键假设，或需要等待故障再次出现时，完整读取 [客户侧采集脚本规范](references/collection-script.md)，再生成一个与本次故障匹配的 Bash 脚本。

先向工程师输出材料缺口和采集目的。只有当手工收集容易遗漏、需要时间对齐/连续观测，或工程师明确需要可执行采集器时才生成脚本；简单缺少系统版本、CPU 架构或少量日志时，优先给出清单和单条命令。

脚本必须围绕当前假设收集信息，不生成无差别的整机支持包。交付时同时提供：

1. 脚本用途和它要验证的假设。
2. 适用发行版/桌面/服务及普通用户或 `sudo` 要求。
3. 预计运行时间、磁盘占用、性能影响和敏感数据范围。
4. 保存位置、压缩包名称、校验值和客户预览/脱敏方法。
5. 精确运行命令、成功标志、失败后的替代步骤和清理方法。

生成后至少执行 `bash -n`；环境存在 `shellcheck` 时也执行。若无法在兼容 Linux 环境验证，明确说明只完成了静态检查。不得把未经验证的脚本描述为可直接用于生产。

收到采集包后，回到“解析输入证据”，按 manifest 和时间线分析；不要反复生成范围不断扩大的脚本。第二轮采集只能针对第一轮暴露出的具体缺口。

## 5. 确认根因、判断 Bug 性质并给出决策方案

结论必须包含：

- 直接触发因素
- 根本原因，或当前最深的已证实原因
- 放大因素及影响范围形成机制
- 关键证据链与反事实
- 置信度：已证实 / 高 / 中 / 低
- 未执行检查和仍存在的不确定性

根因达到“已证实”或“高”置信度后，完整读取 [解决方案与报告规则](references/resolution-and-report.md)。先判断 Bug 性质和处理路径，再给出：

1. 必要时的应急止损方案。
2. 局部修复或优化方案。
3. 重构、重做或架构治理方案。
4. 需要部门评估和拍板的决策事项。

每个方案说明适用条件、具体改动、影响范围、风险、停机需求、验证方法、回滚触发条件和回滚步骤。解释为什么推荐该方案，并指出未选择方案的主要代价。

根因只有中/低置信度时，可以给出可逆的条件性缓解和验证方案，但不能把它描述为确定修复；分析报告标记为“草稿/根因待确认”。

给出解决方案后默认停止在“待决策”，不马上实施：

- 应急止损只有在影响仍在扩大、方案可逆且用户明确授权后才可执行。
- 局部优化必须先确认改动范围、负责人、版本计划和验收标准。
- 涉及重构、重做、公共组件、协议、数据结构、兼容策略或多个部门时，输出方案比较和部门评估材料，等待明确决策，不自行选择或实施。
- 需要修改产品代码时，输出“开发实施说明”，包含受影响模块、修改方向、接口/兼容影响、测试范围、发布和回滚要求，然后停止；即使用户要求“直接改代码”也不在本 Skill 中实施。
- 已由其他团队实施的变更可以根据用户提供的 diff、版本和验证结果更新到报告中，但不得把建议方案写成已执行。

重启、kill、挂载或文件系统修复、驱动/内核/包变更、权限与安全策略修改、桌面配置重置等操作，还必须说明影响、恢复条件与回滚方法并单独取得授权。

验证方案必须回到原始复现条件，并检查相关日志、服务状态、资源、性能和兼容路径；不能只看修复命令是否成功。外部团队提供实施结果后，可以分析验证证据并更新报告；若验证失败，建议停止扩大变更、回滚并重新打开假设。

## 6. 记录 Bug 分析报告

无论是否实际执行修复，都要按 [排查报告模板](references/report-template.md) 生成报告：

- 能写入用户指定位置时，保存为用户指定文件。
- 未指定位置但当前工作区可写时，保存为 `bug-reports/<case-id>-<YYYYMMDD-HHMMSS>.md`；case ID 必须清理为安全文件名。
- 无法安全写文件时，在回复中输出完整报告，并明确标记“未保存到文件”。

同一事件已有报告时优先更新原报告并增加修订记录，避免产生互相冲突的多个版本。报告必须区分“建议”“待部门评估”“已批准应急处理”“已批准优化”“已批准重做”“外部已执行”“已验证”“已回滚”；不能把候选方案写成部门决定，也不能把已批准方案写成已经实施。

## 输出

最终回复应概述根因、Bug 性质、建议处理路径、待决策事项和当前实施状态，并提供 Bug 分析报告的文件路径或完整报告内容。简单问题可以省略报告中的空章节，但必须保留输入证据、根因置信度、关键证据、性质判断、候选方案、决策状态、回滚、验证、证据缺口和未执行项。

- 使用中文解释，命令、日志、错误码和界面原文保持原样。
- 不粘贴无关的大段日志；引用关键时间窗口和证据位置。
- 图片、日志、core、pcap、环境变量和采集包可能包含客户数据、账号、路径、IP、Token 或业务内容，提醒脱敏并限制共享范围。
