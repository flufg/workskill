# 文档审查

上传前对每份可提取正文的文档做审查。整理目的是交出一份可供领导或同事审阅的方案或报告：表述专业、结构清楚、事实可靠，同时保持原意，内部一致。

未输出审查报告、用户未确认前，不得上传。

## 文档体例

面向审阅者组织正文，不要改写成口语提纲。

| 内容 | 要求 |
|---|---|
| **方案 / 报告正文** | 必须保留：目标、范围、方案要点、实施步骤、接口与实现要点、产出与结论。沿用原文已有的正式标题。 |
| **约束与前提** | 不是必须单列。能并入方案或实施步骤的，并入后不再单开「注意事项」。 |

禁止把章节改成「要做什么」「注意什么」。原文若已使用这类口语标题，改为「目标」「方案」「实施步骤」等书面标题，不反向替换。

书面语要求：

- 用「将实施」「采用」「实施范围包括」等陈述，不用「咱们」「搞一下」「搞定」「别 xxx」
- 标题用名词或动宾结构的正式说法，例如「目标」「实施方案」「交付说明」
- 读起来应像提交审阅的材料，而不是工作备忘或聊天记录

不保留：

- 重复出现的同一段信息
- 「不要 / 禁止 / 切勿 / 严禁 / 避免做 xxx」这类否定句，以及只列出反例、禁令的章节

「不要 xxx」默认当冗余删除。不要改写成「注意什么」，也不要用它当标题。若它其实是在说明某条已有步骤的做法，把做法并入该步骤的正面表述。

## 硬性边界

可以做：

- 按方案 / 报告结构整理章节，保留或规范原文标题，不发明新的任务或结论
- 把口语标题改为书面标题（「要做什么」→「目标」或「实施方案」）
- 调整标题层级和段落顺序（原文顺序没有因果或时间依赖时）
- 合并同主题段落，拆开混杂段落
- 统一同一概念的用词
- 删除重复句段和「不要 xxx」
- 把否定句里已有步骤的做法，改写成该步骤的正面表述
- 修正明显笔误、标点和破碎句子，前提是改后意思不变
- 原文若已有独立约束说明且未被步骤覆盖，可以原样保留（改用书面表述）；也可以按用户确认删掉。不主动补写「注意事项」
- 按表格使用边界决定：查/比才用表，走/论不用表；对照允许 2 行；属性卡用长表；阶段信息默认有序列表

不可以做：

- 把「目标」「方案」「实施步骤」等正式标题改成「要做什么」「注意什么」
- 改结论、建议、优先级、责任人、截止日期、数量、版本号、状态
- 改因果关系、条件句、范围限定（如“仅预发”“原则上”“暂不”）——这些若属于方案或步骤，随正文保留
- 补充原文没有的事实、背景、方案、引用或注意事项
- 为了凑结构新建「注意 / 风险 / 禁止」章节
- 把猜测写成确定，或把确定写成猜测
- 跨文档自动“对齐”冲突数据；冲突必须标出来交给用户

## 审查步骤

对每份文档按顺序执行，不要跳过矛盾检查直接整理。

### 1. 提取正文

- Markdown / 文本：直接读
- `.docx` / `.html`：提取纯文本或 Markdown 后再审查
- 会话粘贴：先保存为工作副本
- 无法提取正文的 PDF / 图片 / 二进制：只做文件名、类型、大小和明显误传检查，在报告中标明“未做语义审查”

### 2. 矛盾检查

先找冲突，再整理。冲突包括：

- 同一指标出现不同数字、单位或口径
- 日期、版本、里程碑顺序互相打脸
- 同一事项的状态相反（已完成 / 进行中 / 取消）
- 责任人或接口人前后不一致
- 结论与论据相反，或摘要与正文相反
- 同一术语被定义成不同含义
- 步骤之间互相打脸（例如一步要求立刻删除，另一步要求先确认）

每条矛盾记录：原文位置、冲突双方、是否阻断上传。会改变决策的矛盾默认阻断；仅表述不统一的标为警告，整理阶段可统一用词，但不得选定一个数字去覆盖另一个数字。

### 3. 冗余检查

冗余只抓两类。

**重复**

- 连续或隔段重复的相同段落
- 只换了措辞的同义反复
- 目录、摘要、正文三处复制同一大段
- 已过时的草稿段落与正式段落并存，且内容重复
- 方案或步骤里已经写清的内容，又在别处用不同句子再说一遍

处理：保留信息更完整的一处；两处互补则合并进方案或实施步骤。

**不要 xxx**

识别「不要 / 别 / 禁止 / 切勿 / 严禁 / 避免 xxx / 不能 xxx / 不可 xxx」以及纯禁令列表。

| 原文形态 | 处理 |
|---|---|
| 否定句只是在重复已有步骤 | 删除 |
| 否定句在说明某条已有步骤的做法 | 并进该步骤的正面书面表述，删除否定句 |
| 整节只有禁令、没有方案或步骤 | 删除该节 |
| 原文已有独立约束说明 | 不强制保留；未覆盖且用户未要求删除时可留，改为书面表述，不改成「注意什么」 |

不要把「不要 xxx」改写成注意事项来“保全约束”。

### 4. 整理

在矛盾已标记、冗余已处理的前提下，整理成可供审阅的方案或报告：

1. **正文**：目标、方案要点、实施步骤、产出与结论；一段只说一件事；步骤保持原顺序。优先沿用原文正式标题。
2. **约束说明**：不强制单列。没有独立约束就不要这一节，更不要写成「注意什么」。
3. 术语按全文首次出现的规范说法统一；全文改为书面语。
4. 产出整理稿，并列出「改了什么 / 没改什么」，其中单独列出：口语标题如何改为书面标题、删除了哪些重复、哪些「不要 xxx」被删除或并进步骤、表格如何取舍。

整理稿必须能回溯到原文。不确定的改动标为「未改，需用户确认」，不要自行定稿。

## 表格使用边界

审查时对每张表和每段「像表的叙述」做一次取舍。不为版式好看而建表，也不把本该对照的清单留在长段落里。

| 阅读任务 | 形态 | 原因 |
|---|---|---|
| **查**：按名字找属性 | 表 | 扫描，不靠通读 |
| **比**：同一维度横纵对照 | 表 | 对齐才比得动 |
| **走**：然后呢、第几步 | 有序列表 | 表会打乱顺序感 |
| **论**：为什么、所以、除非 | 段落 | 表装不下推理和例外 |

任务冲突时，走或论压过查或比，不用表。拿不准时不用表。

判定顺序：

1. 读者要干什么：查 / 比 / 走 / 论？走或论则停，改为列表或段落。
2. 条目是否共享同一组**原文已有**字段，并且需要横纵对照或按键检索？
3. 改成表或改成叙述后，信息是否仍能回溯到原文，且不增不减？

「记录」指可对齐的条目（一个对象，或属性卡里的一个项），不是必须多个系统对象。

### 应当用表

查或比，且至少有 **2 个可对齐字段** 时，才考虑用表。不要用「必须 ≥3 条记录」一刀切。

| 场景 | 门槛 | 示例 |
|---|---|---|
| 多对象对照 | 允许 2 行 | 方案 A/B、启用/停用、环境节点角色 |
| 登记簿 / 映射 / 矩阵 | 优先 ≥3 条 | 命令与含义、错误码、覆盖范围 |
| 单对象属性卡 | ≥3 个项，用两列长表（项 / 值） | 模块配置、组件身份字段 |

原文用段落逐条写「对象 A 的字段 1/2/3，对象 B 的字段 1/2/3」时，整理成对照表。单对象不要拍成 1 行很宽的表，改为「项 / 值」长表。

单元格只放可扫描的短语、枚举、ID、条件；解释性文字放到表前或表后一段。1～2 行且读起来就是一句话的，仍改成段落，即使看起来像对照。

### 不应当用表

出现以下任一情况，改为叙述或列表，不保留为表：

| 形态 | 改为 |
|---|---|
| 只有一列，或两列但第二列全是重复说明 | 无序列表 |
| 只有 1～2 行，且读起来是一句话 | 段落 |
| 步骤、时间线，或读者主要跟着做的阶段信息 | 有序列表 |
| 论证、因果、结论推导、例外条件的展开、优缺点列举 | 段落 |
| 为排版、缩进、左右分栏而建的表 | 按阅读顺序还原为正文 |
| 表与前后段落逐句重复 | 留一处；通常留表、删复述，除非叙述含表中没有的限定 |
| 单元格超过约三句，或内嵌另一张表 | 拆开：表只留检索字段，细节整段下沉为小节，不摘要改写 |
| 列数过多，飞书中无法一屏扫读（一般超过 6 列） | 拆成两张表，或保留关键列、其余改段 |

「阶段 × 负责人 × 产物」这类又有顺序又能查的信息，**默认有序列表**，字段写在每一步下面。只有读者明显是在查某阶段的负责人或产物时才可留表：第一列固定为序号或阶段名，禁止重排。拿不准就列表。

流程图、架构关系用图或列表，不用表硬模拟连线。2×2 矩阵若四个格子只需一句话对照，用表；若需要坐标轴语义且已有图，图和表只留更易审阅的一处，另一处不重复展开。

### 整理时允许的改动

- 把对齐良好的并列叙述收成表；把不合格的表打回列表或段落。
- 统一表头用词；删除空列、合并语义相同的列。
- 空单元格：原文没有对应值就留「—」，不编造。
- 表题用书面名称，例如「授权模式」「发布组件字段」，不用「如下表所示」单独成段凑字。
- 表头只能是原文已经在用的字段标签；原文没写的维度（如「是否必须」）不得加列。

不可以：为了凑表而补充原文没有的列或行；把有序步骤改成无序表头；把长单元格摘要成一句（那是改写，不是截取）；用表掩盖矛盾（表内冲突仍按矛盾检查上报）。

审查报告的「表格取舍」写清：保留 / 改为表 / 改为列表或段落，以及原因（点明阅读任务：查 / 比 / 走 / 论）。

## 审查报告

每份文档输出：

```markdown
## 审查：<标题或文件名>

- 来源：
- 是否可提取正文：是 / 否
- 建议：上传 / 先裁决矛盾 / 不上传

### 整理摘要
- 文稿类型：方案 / 报告 / 其他
- 标题与结构：
- 书面语调整：
- 表格取舍：
- 重复处理：
- 「不要 xxx」处理（删除 / 并进步骤）：
- 明确未改动的事实与结论：

### 矛盾
| ID | 位置 | 冲突 | 是否阻断上传 |
|---|---|---|---|

### 冗余
| ID | 类型（重复 / 不要xxx） | 位置 | 处理 |
|---|---|---|---|

### 待用户确认
- 
```

有阻断性矛盾时：展示原文冲突，等待用户选择保留哪一版，或明确「仍按原文上传」。用户未裁决前不上传。

用户确认的对象是整理稿，不是「可以上传」四个字。确认后，后续上传必须使用整理稿，不得再改回未审查原文，除非用户要求保留原文。

## 批量文档

多份一起上传时，额外做一次跨文档检查：

- 同一项目的状态、数字、负责人是否互相矛盾
- 是否重复上传已在 `config/wiki-target.json` 的 `nodes` 里出现过的标题
- 多份文档是否重复写了同一条目标、方案或步骤

跨文档矛盾只报告，不擅自改某一份去迁就另一份。
